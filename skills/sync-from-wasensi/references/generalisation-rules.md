# Generalisation rules

The decisions made when Wasensi's skills, guides and templates were ported into this plugin. A difference between the two sides that one of these rules explains is deliberate: keep it. Add a rule here whenever the user settles a new one.

## File map

| Wasensi (`origin/staging`) | Plugin |
|---|---|
| `.claude/skills/<name>/SKILL.md` | `skills/<name>/SKILL.md` |
| `docs/guides/engineering-workflow.md` | `guides/engineering-workflow.md` |
| `docs/guides/code-review.md` | `guides/code-review.md` |
| `docs/guides/skills.md` | `guides/skills.md` |
| `docs/templates/prd.md`, `epic.md`, `issue.md` | `templates/prd.md`, `epic.md`, `issue.md` |

Not ported:
- `.claude/skills/gitnexus/*`: generated by GitNexus.
- `docs/templates/task-list.md`: the plugin has no task-list file (see Workflow). Removed upstream too.
- Any other `docs/guides/*.md` (stack guides such as backend conventions or frontend): repo-specific. Propose a new guide only if it is about the workflow, not the stack.

Plugin-only files (no upstream source):
- `.claude-plugin/plugin.json` and `skills/sync-from-wasensi/`: never changed by a sync, except the rules file in step 11.
- `README.md`: its wording is plugin-only, but its stage table is kept in step with the skills (step 5).

Plugin-only lines inside ported files (keep them; they are not upstream drift):
- Each skill's "Paths below starting `../../`..." line and its "Read first" line naming plugin guide sections.
- Pointers from a skill to a plugin guide section ("apply the size limits in the guide", "titled and labelled as the guide says").
- The guide's whole "Repository settings" section.

## Source of truth

- Within the plugin, a skill wins over a guide or template that disagrees with it; fix the guide or template.
- A repo's own `CLAUDE.md`/`AGENTS.md`, guides and templates win over the plugin's. This is written in the guide's "Repository settings" section, which is plugin-only.

## Paths and references

| Wasensi | Plugin |
|---|---|

## Domain and stack

- **Tenant isolation** becomes conditional "data isolation": applies when the project is multi-tenant or holds per-user data; "tenant" becomes "tenant or user".
- **Wasensi specifics dropped or made generic**: Laravel, Pest, Pint, PHPStan, Rector, Scribe, Biome, Vitest names; PostgreSQL/MongoDB (becomes "which store"); Gupshup (becomes "third-party"); `webhook-receiver/` (becomes "other services in the repo"); `App\Helpers\Money`, `TenantBillingService` (becomes "the project's money helper, idempotent ledger writes"); Form Requests (becomes "validated at the boundary"); React Query data-flow line (becomes "the repo's documented data flow"); roles list (tenant member, super admin).
- **GitNexus** is optional: "with GitNexus when its index is available, otherwise read the code and search callers". Never required.
- **Dev stack per session**: Wasensi's `make up AGENT=<name>`, `make dev-list`, `make dev-forget` become "a dev stack of your own (own ports and data) if the repo supports one; otherwise one at a time".
- **CI tests skipped**: Wasensi's `skipIfMongoUnavailable()` example is dropped; the rule "confirm new tests appear as passed, not skipped, in the job log" is kept.
- **Also dropped as Wasensi conventions**: "migrations contain schema only"; authorisation "as middleware on its route group"; protected-branch pre-commit hook; `make pre-commit-install`.
- **Host static checks on changed files**: Wasensi's Pint/PHPStan commands and #745 become "when the repo-wide target also fails on untouched files, run the checks on the changed files only".
- **Repo script tests**: Wasensi's `scripts/tests/*.test.sh` row becomes a generic "Repo tooling and script tests" row in the verifier's check table.
- **Removed outright**: Wasensi issue and PR numbers (#651, #643, #693, #745 ...), wiki page names, CI "Gate 1/2/3/4" names, ports 8010/5173, `make` targets, `scripts/run-docker-tests.sh`, `scripts/tests/*`, `.github/ci-scripts/`.
- **Worktree setup**: Wasensi's `make install` and `make doctor` in a new worktree become "install the repo's dependencies, and run its setup or health check if it has one"; the matching verifier trap names no tools.
- **Browser-tool output**: `.playwright-mcp/` is kept only as an example of output a session deletes after browser checks.
- **Script-test coverage**: "only CI Gate 1 runs `scripts/tests/bootstrap.test.sh`" is dropped; the rule "any hook or CI job that runs them covers every new script" is kept.
- **Dev-stack env overrides**: the `AGENT` stack's `VITE_API_BASE_URL`/`VITE_REVERB_PORT` trap becomes "a dev stack can export variables that override the repo's `.env` files".
- **Board status script**: `implement-issue/set-status.sh` is ported verbatim (it only uses `gh` and the current repo); the skill calls it as `set-status.sh` "in this skill's folder", not by Wasensi's `.claude/skills/...` path.
- **SSH push drop**: "while the pre-push suite runs" becomes "while a long pre-push hook runs".
- **Also dropped**: `scripts/tests/makefile-targets.sh`; the dev Mongo database name (`wasensi_messages`); the React Query `mutate()` per-call callbacks bullet in the code review guide (stack-specific, like the data-flow line); the "second Vite" in the PID trap becomes "a second server".
- **Deleted-file review bullet**: "the `Covers:` lines in `docs/features/`" becomes "any `Covers:` lines in `docs/`" (`/docs-updater` puts one on every doc).
- **Routes-cache trap** (`bootstrap/cache/routes-v7.php`, `ScribeDocsAuthTest`) becomes the verifier's generic "local caches from a running dev stack can leak into test runs" trap.

## Skill-specific

- **`/verifier-locally`**: discovery-based. Its check table lists kinds of checks and where to find their command (CI, hooks, Makefile, package manifests), not Wasensi commands. Wasensi traps are ported only when they generalise (for example "a script that prints NOT RUN and exits 0 is not a pass"). The plugin's "Discover the checks" and "Build the check table" steps are plugin-only.
- **`/docs-updater`**: one `docs/<component>.md` per component the repo has, instead of Wasensi's backend/frontend/webhook-receiver files; `docs/guides/` and `docs/templates/` are left alone.
- **`/create-tasks`**: creates issues directly; no task-list file. The epic comes from `/create-prd` on approval; `/create-tasks` creates one only if missing.
- **`/refine-issues`** and `templates/issue.md`: WHAT / WHY / HOW body.
- **`guides/skills.md`** says "Skills that end with an 'Improve this skill' section", not "Every skill ends with": `/sync-from-wasensi` and some ported skills have none.
- **"Improve this skill" sections**: approved edits go to the plugin source repo (`~/Documents/Projects/Personal/ai-workflow`), committed as `chore: update /<name> skill - <what changed>`, never in the project being worked on. "Facts about one codebase go to its `tasks/lessons.md` or docs" and "in any repository" wording is plugin-only.
- **Epic template** also lists the PRD's `priority:` label: plugin-only.
- **`/create-prd`** interview bullet giving visual or layout options an ASCII mockup in the `AskUserQuestion` preview: plugin-only.
- **`/create-prd`** "Stop and ask" also names security rules ("a data-isolation, security or billing rule"): plugin-only.
- **`/docs-updater`** plugin-only additions: fold `docs/<component>.md` into `docs/architecture.md` in a single-component repo; ask before removing a doc you are not sure was generated; the "(CI requires it)" reason for the issue reference is dropped.

## Workflow

- The guide's stage 2 is "Tasks" (child issues), not "Task list". Its "Tasks" section keeps the size limits, shared-file ownership, short dependency chains, shown in the breakdown before issues are created. Waves are not ported (removed upstream in 68dce995). `Parallel: yes/no`, `Area`, `Changed`/`Dropped` markers and `docs/tasks/<slug>.md` are not ported.
- An agent never merges a PR and never opens the release PR.
- The guide's Implementation section has a "Data isolation" bullet: plugin-only, since Wasensi states that rule in its `CLAUDE.md`, which the plugin cannot ship.
- Project status for a new issue is copied from the team's other *unstarted* issues, not "refined, unstarted": in the plugin, issues join the project at `/create-tasks`, before they are refined.
- "Each push, and each edit to a PR's title or body, starts a full CI run" is ported hedged: "and so may each edit", since PR-edit triggers depend on the repo's workflows.
