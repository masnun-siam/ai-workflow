# Implement an issue

Input: a GitHub issue number, or an epic number (step 0 picks the issue). Output: a pull request into the base branch that does what the issue says, verified locally and green in CI, marked Ready for review. The issue body (WHAT/WHY/HOW, written by `/refine-issues`) and the PRD it links are the source of truth.

Paths below starting `../../` are relative to this skill's folder, at the plugin root. Read first: `../../guides/engineering-workflow.md` ("Repository settings" to resolve the base branch, "Implementation", and "Branches, commits and pull requests"), and the repo's `tasks/lessons.md` if it has one.

## Steps

0. **Pick from an epic.** Skip this step unless the number carries the `epic` label (an issue that only has sub-issues is not an epic). List its open children (`gh issue view <epic> --json subIssues`) and read each one (`gh issue view <c> --json state,labels,blockedBy,projectItems`). First promote: each child in Backlog that meets the Ready condition in `../../guides/engineering-workflow.md` (Project fields) moves to Ready (`set-status.sh <c> "Ready"`, in this skill's folder). Then take the lowest-numbered child in Ready with no open blocker, whoever is assigned, and claim it at once so a parallel session does not take it too: re-read its status, take the next one if it is no longer Ready, otherwise move it to In progress and assign it as step 1 says. Continue with it as `<n>`. If there is none, list each open child with its status and open blockers, and stop.

1. **Stop if it is blocked.** Note the start time (step 15 needs it). Read the issue (`gh issue view <n> --json state,labels,body,comments,blockedBy,parent,assignees`). If any issue in `blockedBy` is still open, stop and tell the user in one or two lines which issue blocks it and what it waits for. Do nothing else. Also stop before creating a worktree if the body has no WHAT/WHY/HOW or says refinement is pending: tell the user to run `/refine-issues <n>`. A detailed PRD is no substitute. If either stop applies and step 0 claimed the issue, undo the claim before telling the user: move it to Backlog (`set-status.sh <n> "Backlog"`) and `gh issue edit <n> --remove-assignee @me`. On the refinement stop also remove the stale `refined` label (`--remove-label refined` on the same edit), so step 0 does not promote and pick it again; `/refine-issues <n>` adds it back.

   If neither stop applies, then unless step 0 already claimed it, move it to In progress on its project board: `set-status.sh <n> "In progress"` (in this skill's folder). If that fails (not on a board, no `project` token scope), carry on and say so in the report. Then make the current user its only assignee: `gh issue edit <n> --add-assignee @me`, plus `--remove-assignee <login>` for every other login in `assignees`.

2. **Read everything about it.** The issue body and every comment (a later comment can correct the body; follow the correction), the PRD it links, and its parent epic. If the issue has no WHAT/WHY/HOW, or something needed is undecided, stop and ask the user with `AskUserQuestion`, recommended option first with the reason; suggest `/refine-issues` when the gap is large. Never make a product or design decision yourself.

3. **Work in its own worktree.** Fetch, then create a branch and worktree from the latest `origin/<base>`, named with the issue number, under `.worktrees/` (for example `git worktree add -b issue-<n>-<slug> .worktrees/<n>-<slug> origin/<base>`). Then install the repo's dependencies in it, since a fresh worktree has none, and run its setup or health check if it has one: fix what it lists, commit hooks included, before the first commit. Do all work there, so several issues can run on the same machine without conflict. For a bug, reproduce it here first (with a dev stack of your own when it needs the running app) from the issue's steps or evidence; if it does not reproduce, stop and tell the user before changing code. Issues with no open blocker between them can be implemented at the same time, one session and worktree each; never touch another session's worktree, branch, stash or dev stack.

4. **Understand the code before changing it.** Read the code the issue names, its callers and the closest existing feature, and check the impact of every symbol before editing it: with GitNexus impact analysis when its index is available, otherwise by searching for every caller, and again whenever the scope grows mid-PR. Where GitNexus does not index something (type aliases, build files, shell scripts, config), search its usages across the repo and run the typecheck instead, and say so in the pull request. Read any repo documentation relevant to the area. Follow the surrounding code.

5. **Implement with clean code.** Do what the issue asks, nothing more. Keep the code consistent with the codebase, maintainable and reliable: reuse what exists instead of duplicating it, keep functions small and named for what they do, handle errors and edge cases, and, where the project is multi-tenant or holds per-user data, keep every query scoped as its rules require.

6. **Write the tests** the issue asks for, covering the acceptance criteria and the failure paths.

7. **Keep documentation in step.** In the same pull request, add, update or remove whatever repo documentation this change makes new, wrong or obsolete.

8. **Handle what you find on the way.**
   - A bug, refactoring opportunity or other problem that can wait: stop, and file it in two steps. Create it with `/create-tasks` given what you found and where, then fill it with `/refine-issues <new issue number>`; never create one with a bare `gh issue create`. Then carry on.
   - One that blocks this issue: fix it in this pull request, in its own commit, and say why in the pull request.
   - Stale, outdated or wrong information in another issue of the same epic: comment on that issue with what is wrong and what is true (proven by a test or a run, not guessed), so the agent working on it knows.

9. **Run every check locally before pushing.** CI is expensive, so nothing goes to CI that has not passed here. Run `/verifier-locally` and fix every failure it reports locally.

10. **Verify it works in the app.** Start the app locally the way the repo's docs say. When other sessions may be running, use a dev stack of your own (own ports and data) if the repo supports one, and stop it when done; never use or restart a stack another session is using. For checks that need data, use the repo's seed or demo-data command if it has one. For anything a user or API client can see, check each acceptance criterion in a browser with whatever browser tool you have, or against the API for backend-only changes. Check the failure paths too. If you cannot run it, say exactly what was not verified. After running a dev stack, clear the local caches it leaves before pushing, as the `/verifier-locally` trap says, when a push hook runs the tests.

11. **Commit.** Small commits with clear messages that reference the issue, in the format the guide gives unless the repo states its own. Let every hook run. Never use `--no-verify`; if a hook is broken rather than your code, stop and ask the user.

12. **Review it before pushing.** CI is expensive, so the review runs on the local branch, not after CI. Run `/pr-review <branch>` on the committed work. Fix every Critical and Major finding locally in new commits and re-run the affected checks; fix the rest or say in the pull request why not. Re-review the new commits the same way until no Critical or Major finding is left.

13. **Merge, push and open a draft pull request.** Merge the latest `origin/<base>` into the branch and re-run the affected checks: two pull requests green on their own can still break the base branch together. Then push and open a draft pull request into the base branch, with a body that links the issue (`Closes #<n>`), says what changed and why, how it was verified locally, the `/pr-review` verdict and what was done with each finding, and a **Learnings** section with the same points you log on the issue in step 15 (leave it out if there are none). If an SSH push drops ("Broken pipe") while a long pre-push hook runs, push over HTTPS with `gh auth git-credential` as the credential helper; the hooks still run. An edit of the title or body may run only light checks, not the full CI; changing the base branch may need a push afterwards to run CI against the new base.

14. **Get it green, then mark it ready.** Watch CI (`gh pr checks <pr> --watch`). Fix every failure locally first, re-review a non-trivial fix as step 12 says, then push to the same branch. If `gh pr checks` reports no checks, run `gh pr view <pr> --json mergeable` first: GitHub runs no CI for a conflicting pull request; merge `origin/<base>` again only then, or when another push is needed anyway. Green is not enough on its own: read the test job log (`gh run view <run> --job <job> --log`) and confirm the new and changed tests appear as passed, not skipped. A pull request with failing or unfinished CI is not finished work. Read every review comment and conversation on the pull request; fix it or reply with why not. Only when CI is green and every comment and `/pr-review` finding is handled, mark it ready (`gh pr ready <pr>`), then move the issue to In review (`set-status.sh <n> "In review"`; on failure carry on and say so in the report). Never merge it yourself.

15. **Log learnings on the issue.** Add short, to-the-point comments on the issue for anything learned that the next person would want: a surprise in the code, a wrong assumption in the issue, a check that failed and why. Skip it if there is nothing. If the whole run, from step 1 to marking it ready, took more than 50 minutes, always log it: how long it took and which steps took the time. Put it in the pull request's Learnings section too, or in a pull request comment starting with `## Learnings` (`/skill-feedback reconcile` finds it by that heading).

16. **Report** the pull request link, the `/pr-review` verdict and what was done with each finding, what was verified locally and how, follow-up issues created, comments left on other issues, any project board status that could not be set, and anything not done.

## After the pull request is merged

Run this when the user says the pull request for issue `<n>` is merged, often in a new session.

1. **Confirm the merge.** Find the pull request: `gh pr list --state merged --base <base> --search "Closes #<n> in:body" --json number,headRefName,body --jq '.[] | select(.body | test("(?i)closes #<n>\\b")) | [.number, .headRefName] | @tsv'` (the search alone also matches other issue numbers). If not exactly one comes back, list what was found and ask the user which; `<pr>` and `<branch>` are its `number` and `headRefName`. Fetch, then confirm `origin/<base>` has the branch's content (`git diff origin/<branch> origin/<base> -- <the pull request's files>`, or the local branch if the remote one is gone, shows no difference except from later base-branch commits; a squash merge leaves the branch's commits out of the base branch's history). If either check fails, tell the user and stop without changing anything.
2. **Close the issue.** A pull request into a base branch that is not the default branch does not close it: if it is still open, `gh issue close <n> --reason completed --comment "Merged in #<pr>."`. Then `set-status.sh <n> "Done"`.
3. **Clean up.** Stop and release its dev stack if it had one of its own, remove the worktree and its local branch, delete the remote branch if GitHub kept it (`git push origin --delete <branch>`), then in the main checkout fetch and check out the latest base branch.
4. **Unblock what it blocked.** List the issues it blocked (`gh issue view <n> --json blocking`) and read each one (`gh issue view <b> --json state,labels,blockedBy,projectItems`). Each one in Backlog that now meets the Ready condition in `../../guides/engineering-workflow.md` (Project fields) moves to Ready (`set-status.sh <b> "Ready"`), with a comment that it can start now.
5. **Report** the closed issue, the issues moved to Ready, those still blocked and by what, and any step that failed.
