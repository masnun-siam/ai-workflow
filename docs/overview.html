ai-workflowA Claude Code plugin that turns a GitHub issue into a reviewed pull request

Give it a GitHub issue. Get back a reviewed pull request with passing CI.

ai-workflow runs a team of specialised AI agents, called Stations, one after another on a single issue. One plans, one writes failing tests, one writes the code, one checks it running, one reviews it. A small Python engine decides who goes next, and every Station must show evidence that another check then tries to disprove. You stay in charge. It stops for you exactly three times and it never merges anything.

The whole journey, from idea to merge

The three moments it asks for you

Anything else it runs into (a missing detail, a flaky check) it records and reports at the end instead of stopping. There is no fourth gate by design.

Gate 1

Approve the plan

The planner writes one combined test and implementation plan. You approve, revise (as many times as you like) or abort.

Gate 2a

Confirm a risky finding

Only fires if a review finding needs human judgement, such as an irreversible data operation. Choose "Confirmed, continue" or "Hold here".

Gate 3

Final handback

A report with the PR, CI verdict, open review threads, lessons learned and anything it decided on its own. You merge, or not.

What problem it solves

Handing a ticket to an AI agent usually yields code that looks right, with nothing proving it is. This repo splits the work between agents that each own one job, forces tests to fail before the code exists, checks the running feature, and has a reviewer with fresh eyes read the diff. Claims without proof get rejected by code, not by trust.

Try it

claude plugin marketplace add <path-to-this-repo>
claude plugin install ai-workflow@ai-workflow
/ai-workflow:run-issue 42 --lean

Needs an authenticated gh CLI and Python 3.10+. Docker, Slack, GitNexus and Obsidian are optional extras. The README is written so you can hand the repo to Claude Code and say "set this up".

From a rough request to buildable tickets

The pipeline only works if the issue is clear. Before /run-issue ever runs, three commands turn whatever you have into well-specified, small, ordered GitHub issues. This is where most of the quality is decided.

Ticket refinement

/gh-issue never writes code. It only ever creates an issue, even for a one-character fix. If a fix is obvious, it goes into a Proposed Fix section of the issue instead of being applied.

Task breakdown

Every request is decomposed after the interview, whatever its size. A task is a single-layer deliverable: a database migration, service logic, one API endpoint (request and resource count as one unit) or one UI unit. Docs and config work follow the same limits, split by file or section.

Size rule for each task
Touches 3 or fewer production files (tests do not count)
1 to 4 acceptance criteria
One verify command
Adds no new dependency
An endpoint needing more than 3 files is split by file group, for example route and controller first, then request and resource. The cap is never waived.

A task that fails the rule is split and the list rebuilt before you ever see it. You then get one question with two choices: Create as shown or Let me edit the list. Editing loops with no round limit. A requested merge that would break a limit is declined, with the reason shown.

One task

It becomes a single issue, and nothing is saved to disk.

Two or more tasks

The list is saved, then filed as flat issues, one per task, each standalone and created in dependency order. Context is inlined, so a task body never needs another issue to be understood. Each issue is labelled refined and prd-<slug>.

Dependencies

Edges are written as Depends on: task k and can only point at earlier tasks. At creation each one is rewritten as Depends on: #n using the real issue number. /run-issue is then run on each issue, dependencies first.

Where the task list is saved, and what happens on failure
  • Local (always): docs/tasks/<slug>.md, never committed by the command.
  • Obsidian (optional): a Tasks.md note under the project and feature folder, never overwriting an existing one.
  • GitHub wiki (optional): Tasks-<Title>.md, pushed only after a separate confirmation.
  • If the file already exists you choose a new slug, skip the save, or Resume this list. Resume creates only the tasks without an issue number and checks existing prd-<slug> issues first, so nothing is created twice.
  • If a create fails, the command reports what exists and what is missing, then offers Retry the missing ones or Stop here. Created issues are never closed or deleted, so a partial list is recoverable.

Definition of Ready

Before spending a pipeline on an issue, run-researcher scores it against six items. The result is advisory. Gaps are printed above the plan at Gate 1, where you decide with the plan in front of you.

#ItemPasses when
1Problem and whyStates the problem and why it matters, not only a solution. "Add a status column" is a solution.
2ScopeExplicit in-scope and out-of-scope boundaries.
3Acceptance criteriaTestable. Each one becomes at least one automated test, so "works correctly" does not count.
4Affected surfaceModules, services, endpoints or screens, grounded in the code.
5Non-functional constraintsPerformance, security, authorization, migration, compatibility. "None" is valid.
6Dependencies and blockersOther issues, specs, ordering, or an upstream PR that must land first.

A borderline issue can be normalised: gaps filled with explicitly stated assumptions that Gate 1 shows you. An assumption is always recorded and shown, never silently adopted. If one search of the code answers a missing item, that is an assumption, not a gap.

What /intake and /prd each produce

/intake returns a brief and a type (bug, feature, task or improvement). It never creates issues.

  • Sentry link: title, culprit and stack trace, occurrence counts (first and last seen, events, users, release), and an optional root-cause hypothesis labelled unverified.
  • Requirements file: goals, scope and acceptance criteria in the document's own words. If it holds several independently shippable outcomes, you pick one, or --whole keeps every candidate for /gh-issue to split.
  • Obsidian note: the note body verbatim, only on an exact title match.
  • Free text: wrapped as a summary with a source line.

/prd covers the what and why only. It scans the code first, so its questions are informed, then interviews you across: problem and users, goals and non-goals, testable requirements with acceptance criteria, edge cases, success metrics, rollout and dependencies. The PRD has Overview (with codebase context), Problem, Users, Goals, Non-goals, Requirements (FR-1, FR-2 each with an acceptance check), Edge cases, Success metrics, Decisions, Open questions and Related. You review the full draft before anything is saved to docs/prd/<slug>.md, the vault or the wiki. The next step it offers is /gh-issue.

The pipeline behind /run-issue

One command drives every step. Each Station does one thing, writes a numbered JSON file into the run folder, and hands off. The engine reads that file and picks the next Station.

When a Station is wrong: bounces and escalation

Work can be sent back to an earlier Station. Each pair gets two bounces. A third one escalates the run.

Full mode vs lean mode

Full mode is the default. Lean mode is picked automatically for issues labelled lean, or with --lean. The CI gate applies to both.

Epic mode: parent issues with sub-issues

If the issue is an existing parent with sub-issues, /run-issue runs the children as a dependency graph. Independent children run in parallel. A dependent child builds its branch on top of its parent's branch once the parent has a PR open. The whole epic still has only three gates.

Note that /gh-issue no longer creates epics as of 1.9.0. Epic mode only applies to epics that already exist.

What the first phases do
  • Preflight. Stops if the checkout has uncommitted changes. If you passed free text, a Sentry link or a file instead of an issue, it runs /intake and /gh-issue first. If that files two or more issues, it prints them and stops cleanly. You then run each one, dependencies first.
  • Researcher. Scores the issue against a Definition of Ready. Gaps are shown at Gate 1 and never stop the run.
  • Worktree and stack. A sibling checkout on a new branch, plus (if the repo has a test compose file) a capped, locked Docker stack, one per project at a time.

Under the hood

The design rule is that anything mechanical moves out of the prompt text and into code. The orchestrator does not eyeball a decision it can compute.

One folder per run

Each Run gets <runs_dir>/<owner>-<repo>-issue-<n>/. It holds run.json (the Ledger: roster, current Station, bounce counts, trace, and a context map with branch, PR and CI) and one numbered file per Station.

run.json
00-readiness.json   researcher
10-plan.json        planner
20-tests.json       sdet
30-build.json       dev
40-verify.json      verifier
50-review.json      reviewer
60-fix.json         fixer

State lives under $CLAUDE_PLUGIN_DATA (default ~/.claude/plugins/data/ai-workflow), so it survives plugin upgrades.

Every Station answers in one shape

The Envelope is fixed JSON. A passed claim from sdet, dev, verifier, reviewer or fixer must carry the commands it ran.

{
  "issue": 42,
  "station": "dev",
  "status": "passed" | "bounce" | "escalate",
  "attempt": 1,
  "summary": "...",
  "evidence": { "commands": [ ... ] },
  "handoff": { ... }
}

Claims are checked by code

After a Station reports, checks.py runs a post-check that tries to prove the claim false. A refuted claim gets one redo. After that the run moves on and the failure is reported at Gate 3.

StationPost-check
SDETRefused if the test suite is already green. Tests must fail first.
DevThe commit must resolve and no undeclared files may be touched.
ReviewerThe review must actually exist on GitHub.
FixerEvery review thread is resolved and the push happened.

Engine and CLI

engine.py is pure logic with no I/O. route.py does the I/O. bin/aiw is a thin shell wrapper over it. It was named aiw because macOS already has /sbin/route, which shadowed the old name and still exited 0.

Config

config.json holds the policy: models, caps, the human gates. A repo can override any of it with .run-issue.json. Dicts merge and lists replace.

Tests

Plain assert scripts, no framework, no network, no Docker: python3 run-engine/test_engine.py, test_scripts.py, test_ui_board.py.

Known doc drift. The final gate is "Gate 3" in docs/HOW-IT-WORKS.md but "GATE 2" in commands/run-issue.md section 9.3. plugin.json says 14 agents and the README says 12 run-* plus 3. The repo has 15 agent files (12 run-*, plus ship, worklog-runner and gh-issue-factchecker). Also, commands/gh-issue.md says the readiness check "blocks the run" on a gap, while definition-of-ready.md says it is advisory and only surfaces at Gate 1. This page follows definition-of-ready.md. This page uses the actual values.
