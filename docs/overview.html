ai-workflowA Claude Code plugin that turns a GitHub issue into a reviewed pull request

Give it a GitHub issue. Get back a reviewed pull request with passing CI.

ai-workflow runs a team of specialised AI agents, called Stations, one after another on a single issue. One plans, one writes failing tests, one writes the code, one checks it running, one reviews it. A small Python engine decides who goes next, and every Station must show evidence that another check then tries to disprove. You stay in charge. It stops for you exactly three times and it never merges anything.

The whole journey, from idea to merge

The three moments it asks for you

Anything else it runs into (a missing detail, a flaky check) it records and reports at the end instead of stopping. There is no fourth gate by design.

Gate 1

Approve the plan

The planner writes one combined test and implementation plan. You approve, revise (as many times as you like) or abort.

Gate 2a

Confirm a risky finding

Only fires if a review finding needs human judgement, such as an irreversible data operation. Choose "Confirmed, continue" or "Hold here".

Gate 3

Final handback

A report with the PR, CI verdict, open review threads, lessons learned and anything it decided on its own. You merge, or not.

What problem it solves

Handing a ticket to an AI agent usually yields code that looks right, with nothing proving it is. This repo splits the work between agents that each own one job, forces tests to fail before the code exists, checks the running feature, and has a reviewer with fresh eyes read the diff. Claims without proof get rejected by code, not by trust.

Try it

claude plugin marketplace add <path-to-this-repo>
claude plugin install ai-workflow@ai-workflow

Needs an authenticated gh CLI and Python 3.10+. Docker, Slack, GitNexus and Obsidian are optional extras. The README is written so you can hand the repo to Claude Code and say "set this up".

The pipeline behind /run-issue

One command drives every step. Each Station does one thing, writes a numbered JSON file into the run folder, and hands off. The engine reads that file and picks the next Station.

When a Station is wrong: bounces and escalation

Work can be sent back to an earlier Station. Each pair gets two bounces. A third one escalates the run.

Full mode vs lean mode

Full mode is the default. Lean mode is picked automatically for issues labelled lean, or with --lean. The CI gate applies to both.

Epic mode: parent issues with sub-issues

If the issue is an existing parent with sub-issues, /run-issue runs the children as a dependency graph. Independent children run in parallel. A dependent child builds its branch on top of its parent's branch once the parent has a PR open. The whole epic still has only three gates.

Note that /gh-issue no longer creates epics as of 1.9.0. Epic mode only applies to epics that already exist.

What the first phases do
  • Preflight. Stops if the checkout has uncommitted changes. If you passed free text, a Sentry link or a file instead of an issue, it runs /intake and /gh-issue first. If that files two or more issues, it prints them and stops cleanly. You then run each one, dependencies first.
  • Researcher. Scores the issue against a Definition of Ready. Gaps are shown at Gate 1 and never stop the run.
  • Worktree and stack. A sibling checkout on a new branch, plus (if the repo has a test compose file) a capped, locked Docker stack, one per project at a time.

Under the hood

The design rule is that anything mechanical moves out of the prompt text and into code. The orchestrator does not eyeball a decision it can compute.

One folder per run

Each Run gets <runs_dir>/<owner>-<repo>-issue-<n>/. It holds run.json (the Ledger: roster, current Station, bounce counts, trace, and a context map with branch, PR and CI) and one numbered file per Station.

run.json
00-readiness.json   researcher
10-plan.json        planner
20-tests.json       sdet
30-build.json       dev
40-verify.json      verifier
50-review.json      reviewer
60-fix.json         fixer

State lives under $CLAUDE_PLUGIN_DATA (default ~/.claude/plugins/data/ai-workflow), so it survives plugin upgrades.

Every Station answers in one shape

The Envelope is fixed JSON. A passed claim from sdet, dev, verifier, reviewer or fixer must carry the commands it ran.

{
  "issue": 42,
  "station": "dev",
  "status": "passed" | "bounce" | "escalate",
  "attempt": 1,
  "summary": "...",
  "evidence": { "commands": [ ... ] },
  "handoff": { ... }
}

Claims are checked by code

After a Station reports, checks.py runs a post-check that tries to prove the claim false. A refuted claim gets one redo. After that the run moves on and the failure is reported at Gate 3.

StationPost-check
SDETRefused if the test suite is already green. Tests must fail first.
DevThe commit must resolve and no undeclared files may be touched.
ReviewerThe review must actually exist on GitHub.
FixerEvery review thread is resolved and the push happened.

Engine and CLI

engine.py is pure logic with no I/O. route.py does the I/O. bin/aiw is a thin shell wrapper over it. It was named aiw because macOS already has /sbin/route, which shadowed the old name and still exited 0.

Config

config.json holds the policy: models, caps, the human gates. A repo can override any of it with .run-issue.json. Dicts merge and lists replace.

Tests

Plain assert scripts, no framework, no network, no Docker: python3 run-engine/test_engine.py, test_scripts.py, test_kanban.py.

Known doc drift. The final gate is "Gate 3" in docs/HOW-IT-WORKS.md but "GATE 2" in commands/run-issue.md section 9.3. plugin.json says 14 agents and the README says 12 run-* plus 3. The repo has 15 agent files (12 run-*, plus ship, worklog-runner and gh-issue-factchecker). This page uses the actual values.
